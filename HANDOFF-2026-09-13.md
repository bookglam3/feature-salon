Supabase client at module scope, and several construct
`new Resend(process.env.RESEND_API_KEY)` the same way. Next.js evaluates

## READY TO BUILD ONCE UNBLOCKED — the input-trust fix

**Migration (one commit, with the client diff):**

- `price` / `name` / `duration_minutes` / `price_is_from` read server-side
  from `services`. Guard 8 is set-based (`jsonb_to_recordset` + `NOT EXISTS`),
  so restructure it to **return columns**, not only validate.
- `p_line_items` shrinks to `{ service_id, sort_order }`.
- `v_total_duration` sums the **server-side** durations.
- `price_is_from` → `COALESCE(s.price_is_from, false)`.
- **Do not port the client's `?? 30` default.** NULL duration or price →
  `INVALID_SERVICE_DURATION` / `INVALID_SERVICE_PRICE`.
  Counts confirmed on live: `null_dur = 1` (service `tst`, £4, Messenger
  Studio — test data, becomes unbookable, acceptable), `null_price = 0`.
- New guards:
  - `p_date_time` in the future, 2 min grace → `DATE_IN_PAST`
  - not more than 2 years ahead → `DATE_TOO_FAR`
  - not on a `closed_dates` entry → `SALON_CLOSED`.
    `closed_dates.date` is **`DATE NOT NULL`**, `UNIQUE(salon_id, date)`.
    Compare in the salon's zone: `(p_date_time AT TIME ZONE v_timezone)::date`.
    Add `v_timezone` via `SELECT ... INTO` folded into Guard 1,
    `COALESCE(timezone, 'Europe/London')` — Guard 1 currently only does
    `IF NOT EXISTS (SELECT 1 FROM salons ...)`, and some older rows have a
    NULL timezone.
  - `jsonb_array_length(p_line_items) <= 20` → `TOO_MANY_LINE_ITEMS`
- `NO_STAFF_CONFIGURED` replaces `SLOT_UNAVAILABLE` when the salon has zero
  active staff, so a newly onboarded salon gets a truthful error.

**Do NOT touch:** `FOR UPDATE` locking, the inline/oracle drift check, the
oracle call itself, or either INSERT's ordering.

**Client diff ships in the SAME commit** — `app/book/[slug]/page.tsx:444`,
`lineItems` → `{ service_id: s.id, sort_order: i }`. Half of it alone breaks
live bookings: `selTime`/line items feed
`fromZonedTime(\`${date}T${time}:00\`)`, and the signature changes shape.

**The closed-date guard is NEW behaviour.** The booking page references
`closed_dates` zero times today and `slot-availability.ts` doesn't either —
nothing filters closed dates client-side. So a customer can currently pick a
closed day and would hit `SALON_CLOSED` from a slot the picker offered them.
Ship it with the picker filtering closed dates, or at minimum the mapped
error below.

**Error mappings** (client, `app/book/[slug]/page.tsx` — the existing handler

## WHY IT MATTERS

`p_line_items` carries `price` straight from the client into
`appointment_services`. `create-payment-intent` then reads the price back
**from that table** ([route.ts:45](app/api/create-payment-intent/route.ts#L45))
rather than from the request body — a correctly-built defence that is reading
a number the attacker chose one step earlier.

```
client price → appointment_services.price → create-payment-intent → Stripe charge
```

So a crafted payload sets what Stripe actually charges, and the 2% platform
fee with it. This is a live money path with two paying salons on it.

## QUEUED — move the dashboard wizard onto `create_booking_with_services`

Scoped 18 Sep. **Takes the input-trust fix first**, for two reasons: three
of the six findings below cannot be settled until the function body is in
the baseline file, and the fix itself shrinks `p_line_items`, which makes
finding 1 smaller.

**Why it is queued rather than dropped.** The wizard
([app/dashboard/bookings/page.tsx:279](app/dashboard/bookings/page.tsx#L279))
writes appointments with a raw PostgREST `.insert()`. No slot check, no
locking, no `appointment_services` rows. The public booking page goes
through the RPC and gets all three. "Book Again" (`6e7885d`) routes more
of the owner's traffic onto the raw path, which is a real reason to close
the gap — but not a reason to force it closed badly.

**The core finding: it is NOT a drop-in, and the obstacle is design, not
plumbing.** The RPC's guards encode rules that are correct for a member of
the public booking themselves and wrong for the person who owns the diary.
An owner legitimately books last Tuesday, double-books a slot, and opens
on a closed day. Each of those is a guard the RPC exists to enforce.

**The choice to make first.** Either

- **a) `p_owner_booking boolean DEFAULT false`** on the existing function,
  relaxing the client-facing guards when true. One function, one set of
  line-item and locking logic, one place to audit — but the flag becomes a
  privilege, so it has to be unreachable from the public path, and RLS or
  an ownership check inside the function has to prove the caller owns the
  salon. Otherwise it is a new escalation vector on the money path.
- **b) A separate `create_owner_booking`.** Cleaner privilege boundary and
  no risk of the public path tripping the flag, at the cost of two
  functions that must not drift on locking, line items and totals.

Not decided. (a) is smaller; (b) is safer to reason about. Decide it with
the function body in hand, not before.

**The six divergences**, from reading the wizard:

| # | Divergence | Settled? |
|---|---|---|
| 1 | Wizard writes **no `appointment_services` rows** — a single `service_id` column and nothing else. The RPC requires a non-empty `p_line_items`. | Yes — manageable, and smaller after the input-trust fix reduces `p_line_items` to `{service_id, sort_order}` |
| 2 | **Status.** The wizard offers all five (pending/confirmed/completed/no_show/cancelled, [line 931](app/dashboard/bookings/page.tsx#L931)); the RPC has an `INVALID_STATUS` path and the public flow only ever passes pending/confirmed. | **No — needs the baseline** to see which statuses the guard actually admits |
| 3 | **Past dates.** The wizard's date input has no `min` ([line 772](app/dashboard/bookings/page.tsx#L772)). The planned `DATE_IN_PAST` guard would break retrospective entry, which owners do routinely — it is how a walk-in gets recorded. | Yes — a real conflict, needs owner-mode |
| 4 | **Payment fields.** The RPC requires `p_payment_status` / `p_payment_method`; the wizard writes neither. Needs a defined default for an owner-created booking. | Yes — needs a product answer, not a lookup |
| 5 | **Slot check.** The whole point of moving, and also a conflict: owners deliberately overbook. | **No — needs the baseline** to see whether the check is skippable without unpicking the `FOR UPDATE` locking |
| 6 | **Closed dates.** The planned `SALON_CLOSED` guard would block a special opening. | **No — needs the baseline**, and it depends on whether guard 6 ships at all |

**Do not start this by writing the migration.** Start by settling 2, 5 and
6 against the real function, then pick (a) or (b), then write it.

## QUEUED — rendered accessibility check (Playwright + axe-core)

Scoped 18 Sep, **deliberately queued behind the input-trust fix** and behind
the CI env vars, which are half its cost and are blocking other work anyway.

**Why it exists.** Two invisible-text bugs have now shipped past the theme
guard: the hamburger (`rgba(255,255,255,0.55)` on `#FFFFFF`, 1.00:1, `2e52521`)
and the bookings calendar date numbers (`#ECE9F1` on `#FFFFFF`, 1.20:1,
`ef635dd`). Both are the same failure — a VALID palette token used in the wrong
role. `scripts/check-theme.mjs` compares written hex against a ban-list, and
neither colour is banned; both are correct in their real roles. The question
"what is behind this pixel" is only answerable once the page is painted, so no
text-scanning guard can ever catch this class.

**Scope**
- **Six routes:** `bookings` (table AND calendar views), `calendar` (day/week/
  month), `loyalty`, `page` (home), `settings`, `clients`. That is where every
  visual bug so far has lived. Public routes are already covered by the
  Lighthouse runs.
- **Two viewports:** 390 and 1280. The hamburger was mobile-only; the grid
  misalignment only manifested narrow.
- **Auth:** `storageState.json` from a one-time login, on a test account on
  salon `0056ccd1`. Credentials in CI secrets, never the repo.
- **Prerequisite:** the two env vars in the PREREQUISITE section above
  (`SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`). Without them there is no
  build to run Playwright against, locally or in CI.

**Cost:** about half a day, and the auth is most of it. The spec itself is
~40 lines — `AxeBuilder().withTags(['wcag2aa'])` per route per viewport — plus
`npm i -D @playwright/test @axe-core/playwright`.

**What it would have caught:** the hamburger; the calendar dates;
OnboardingChecklist's near-white-on-white; "Dashboard Locked" at `#2a3350` on a
dark panel; staff's dark-on-dark service chip; `#DC2626` at 4.13–4.41:1 across
38 sites; `#10B981` at 2.54:1 across 48 sites. The last two each took a manual
audit pass to find.

**What it would NOT have caught:** the week-grid misalignment (layout, not
contrast) and the inert menu button on 15 routes (renders fine, does nothing).
axe also only sees what is painted at that moment — not hover states, error
states, or unopened modals (e.g. the settings spinner on its dark overlay). It
raises the floor; it does not replace looking.
